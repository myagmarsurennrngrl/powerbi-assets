# 92 — Администраторын гарын авлага

Хэрэглэгч, эмнэлэг, эмч, брэнд удирдах.

Энэ гарын авлага аппын дотор хийх ажлыг тайлбарлана. Серверийн тохиргоо, нөөцлөлтийн талаар
[`82-production-deployment.md`](82-production-deployment.md) болон
[`94-backup-and-recovery.md`](94-backup-and-recovery.md) хоёрыг уншина уу.

---

## 1. Хамгийн чухал үүрэг: эмнэлгийн байршил

Бусад бүх ажлаас чухал. Эмнэлгийн координат эсвэл зөвшөөрөгдөх зай буруу бол:

* эмнэлэг дээрээ зогсож байгаа төлөөлөгч уулзалтаа эхлүүлж чадахгүй,
* KPI-д «хийгдээгүй уулзалт» гэж бичигдэнэ — үнэн бол хийгдсэн,
* төлөөлөгч системд итгэхээ болино.

**Мастер дата** дэлгэцийн дээд хэсэгт «Анхны радиустай хэвээр» гэсэн тоо байна. Энэ бол
тохируулаагүй эмнэлгийн тоо. Зорилго нь **тэг**.

### Байршлыг хэрхэн зөв бүртгэх вэ

1. Эмнэлэг дээр очно.
2. Утасны газрын зураг дээр **үүдэн дээр зогсоод** цэг дээр удаан дарж координатыг хуулна.
3. Аппын **Мастер дата → Эмнэлэг** → тухайн эмнэлгийг нээнэ.
4. Өргөрөг (latitude), уртраг (longitude) бөглөнө. **Өргөрөг эхэлж.**
5. Зөвшөөрөгдөх зайг барилгаас нь хамаарч тавина:

| Барилга | Зөвлөх зай |
|---|---|
| Жижиг клиник | 150 м |
| Дунд эмнэлэг | 200–300 м |
| Том эмнэлгийн цогцолбор | 300–500 м |
| Худалдааны төв дотор | 300 м |

Хамгийн бага 30 м, хамгийн их 2000 м. 30 м-ээс бага бол хотын GPS-ийн алдаанаас бага тул хэн ч
бүртгүүлж чадахгүй; 2000 м-ээс их бол «эмнэлэг дээрээ байна» гэсэн утгаа алдана.

> Апп координат Монголын нутгаас гадуур байвал улбар шар анхааруулга харуулна. Энэ нь ихэвчлэн
> **өргөрөг, уртраг хоёрыг сольж бичсэн** гэсэн үг. Гэхдээ хориглодоггүй — заримдаа хилийн ойрын
> цэг байж болно.

## 2. Хэрэглэгч удирдах

**Нүүр → Хэрэглэгчийн удирдлага**.

### Шинэ хэрэглэгч
1. **+ Шинэ хэрэглэгч**.
2. Нэр, **ажлын и-мэйл**, эрх, менежер.
3. Хадгална.

Систем нэвтрэх бүртгэл **үүсгэхгүй**. Та тусад нь нууц үг олгох хэрэгтэй — доорх «Нууц үг олгох»
хэсгийг үзнэ үү. Тэр болтол тэр хүн нэвтэрч чадахгүй.

**И-мэйл нь зөвшөөрөгдсөн домэйнд байх ёстой** (`monos.mn`). Өөр домэйн оруулбал систем шууд
татгалзана — учир нь тийм бүртгэл хэзээ ч нэвтэрч чадахгүй.

### Нууц үг олгох

Хүн өөрөө бүртгүүлж нууц үг тавьж **чадахгүй**, бас и-мэйлээр нууц үг сэргээж чадахгүй. Аль
хоёулаа и-мэйл ажиллахыг шаарддаг, бидэнд и-мэйл ажиллахгүй. Шалтгааныг
`docs/99-password-login.md` дээр бичсэн.

Тиймээс **эхний нууц үгийг та олгоно**. Компьютер дээрээ, төслийн хавтаст:

```powershell
npm.cmd run dev:set-password
```

1. И-мэйл хаягийг бичнэ.
2. Шинэ нууц үгийг 2 удаа бичнэ (дор хаяж 10 тэмдэгт).
3. `service_role` түлхүүрийг буулгана (Supabase → Settings → API → service_role → Copy).

Дуусахад **нэг SQL мөр хэвлэнэ**. Түүнийг Supabase SQL Editor дээр ажиллуулна.

> ⚠️ **Тэр SQL мөрийг ажиллуулахгүй бол** тухайн хүн нэвтэрч орох боловч «Таны бүртгэл
> идэвхжээгүй байна» гэж заана. Нэвтрэх бүртгэл нь аппын бүртгэлтэй холбогдоогүй учраас.

Нууц үгийг **и-мэйлээр биш**, биечлэн эсвэл дуудлагаар хэлнэ. Мөн «Тохиргоо → Нууц үг солих
дээрээс өөрөө сольж тавь» гэж хэлээрэй — та эхний нууц үгийг мэдэж байгаа тул солих нь зөв.

### Нууц үг мартсан хүн

Яг ижил зүйлийг хийнэ: `npm.cmd run dev:set-password`. SQL мөр нь аль хэдийн холбогдсон бол юу ч
өөрчлөхгүй, тиймээс дахин ажиллуулахад хэвийн.

### И-мэйл өөрчлөх боломжгүй
Үүсгэсний дараа и-мэйл засагдахгүй. Тэр нь нэвтрэх бүртгэлтэй холбогддог тул өөрчилвөл хүн
өөрийн бүртгэлээсээ салах болно. Шаардлагатай бол шинэ хэрэглэгч үүсгээд хуучныг идэвхгүй
болгоно.

### Эрх өөрчлөх
Эрх өөрчлөхөд систем дараах тохиолдолд татгалзана:

| Юу хийхийг оролдсон | Яагаад татгалзсан |
|---|---|
| Сүүлийн администраторын эрхийг хасах | Дараа нь хэн ч эрх сэргээж чадахгүй болно |
| Брэнд хариуцсан төлөөлөгчийг өөр эрх рүү шилжүүлэх | Эхлээд брэндийн хуваарилалтыг дуусгана |
| Бусдын менежер байгаа хүнийг менежер биш болгох | Тэдний төлөвлөгөө, хүсэлтийг хэн ч шийдэхгүй болно |

Эрхийн өөрчлөлт бүр аудит логт бичигдэнэ.

### Идэвхгүй болгох

Хэрэглэгчийг **устгадаггүй** — идэвхгүй болгодог. Устгавал тэдний бүх уулзалт эзэнгүй болно.

Систем дараах тохиолдолд татгалзана:

* өөрийгөө идэвхгүй болгох,
* сүүлийн администраторыг идэвхгүй болгох,
* дуусаагүй уулзалттай хүнийг идэвхгүй болгох (тэр уулзалт үүрд нээлттэй үлдэнэ),
* бусдын менежер хэвээр байгаа хүнийг идэвхгүй болгох.

**Шалтгаан бичээрэй.** Аудит логт хадгалагдана. Хожим «яагаад» гэдэг нь хамгийн их асуудаг
асуулт байдаг.

### Брэнд хуваарилах
Хэрэглэгчийн хуудсан дээр. Зөвхөн **идэвхтэй төлөөлөгчид** хуваарилна.

Хуваарилалтыг дуусгахад **мөр устдаггүй** — дуусах огноо тавигддаг. Учир нь өмнөх уулзалтууд
тухайн үед хариуцаж байсан брэндтэй холбоотой хэвээр байх ёстой.

## 3. Мастер дата

### Эмч нэмэх
**Мастер дата → Эмч → + Шинэ эмч**.

Нэр бичиж эхлэхэд систем **ижил төстэй эмчийг хайж** харуулна. Энэ бол хамгийн түгээмэл алдааны
эсрэг хамгаалалт: нэг эмчийг хоёр өөр бичлэгээр оруулбал уулзалтын түүх нь хоёр хуваагдаж, хоёр
өөр хүн мэт харагдана.

> **Мэргэжлийн тэмдэглэл** талбарт зөвхөн ажилтай холбоотой зүйл бичнэ. Өвчтөний талаарх ямар нэг
> мэдээлэл оруулах нь **хориотой**.

### Брэнд, бүтээгдэхүүн
**Мастер дата → Брэнд / Бүтээгдэхүүн**. Мөр дээр дарж засна.

### Архивлах
Мастер дата **устдаггүй** — архивлагдана. Архивласан бичлэг жагсаалтаас алга болох ч өмнөх
уулзалтууд хэвээр үлдэнэ.

Дараалал: эхлээд **идэвхгүй** болгоно, дараа нь **архивлана**.

Систем архивлахыг татгалзах тохиолдол:

| Юу | Яагаад |
|---|---|
| Төлөвлөгдсөн уулзалттай эмнэлэг | Төлөөлөгчид хийж чадахгүй уулзалт үлдэнэ |
| Дуусаагүй уулзалттай эмнэлэг | Тэр уулзалт хаагдахгүй болно |
| Төлөвлөгдсөн уулзалттай эмч | Мөн адил |
| Хаагдаагүй дараагийн ажилтай эмч | Дуусаагүй ажил алга болно |
| Хуваарилагдсан брэнд | Эхлээд хуваарилалтыг дуусгана |
| Бүтээгдэхүүнтэй брэнд | Эхлээд бүтээгдэхүүнийг архивлана |

Татгалзахдаа **хэдэн ширхэг** байгааг хэлнэ, тиймээс юу засахаа мэдэх боломжтой.

## 4. Аюулгүй байдлын шалгалт

Сард нэг удаа Supabase-ийн **SQL Editor** дээр:

```sql
SELECT * FROM public.fn_security_findings();
```

**Хариу нь ямар ч мөргүй байх ёстой.** Мөр гарвал юу нь буруу байгааг бичсэн байна — хөгжүүлэгчид
хандана уу.

Мөн Power BI ашиглаж байгаа бол:

```sql
SELECT * FROM public.fn_reporting_reader_leaks();
```

Мөн адил тэг мөр.

## 5. Байнга гардаг асуудал

### «Эмнэлэг дээрээ байгаа мөртлөө уулзалт эхлүүлж чадахгүй байна»

Дараалан шалгана:

1. **Мастер дата → Эмнэлэг** → тухайн эмнэлгийн координат. Google Maps дээр шалгаад үнэн эсэхийг
   хараарай.
2. Зөвшөөрөгдөх зай хэт бага байна уу? Том барилга бол 300–500 м болгоно.
3. Тухайн газарт GPS-ийн дохио муу байж болно (подвал, гүн байр). Тэгвэл координат зөв ч
   нарийвчлал хангалтгүй байна — төлөөлөгч **чөлөөлөх хүсэлт** илгээх нь зөв шийдэл.

Хэрэв нэг эмнэлэг байнга гомдол дагуулж байвал координатыг нь өөрөө очиж шалгана уу.

### «Нэвтэрч чадахгүй байна»

| Бичиг | Шалтгаан | Шийдэл |
|---|---|---|
| «Энэ и-мэйл хаягаар нэвтрэх боломжгүй» | Домэйн зөвшөөрөгдөөгүй | Ажлын и-мэйл ашиглаж байгаа эсэхийг шалгана |
| «Таны бүртгэл идэвхжээгүй байна» | app_user бичлэг байхгүй эсвэл идэвхгүй | Хэрэглэгчийн удирдлагаас шалгана |
| «И-мэйл хаяг эсвэл нууц үг буруу байна» | Нууц үг буруу, ЭСВЭЛ тэр хүнд нууц үг олгоогүй байна | `npm.cmd run dev:set-password` ажиллуулна. Мессеж хоёр тохиолдолд ижил байдаг нь зориуд — аль хаяг бүртгэлтэй байгааг мэдэгдэх нь ажилтнуудын жагсаалтыг илчлэх болно |

### «Эмч жагсаалтад харагдахгүй байна»

Төлөвлөгөө үүсгэхэд эмч нь **тухайн эмнэлэгт холбогдсон** байх ёстой. Эмч-эмнэлгийн холбоог
одоогоор аппаас засах боломжгүй — `doctor_clinic` хүснэгтийг Supabase-аас засна. Энэ нь мэдэгдэж
байгаа хязгаарлалт, [`95-known-limitations.md`](95-known-limitations.md) дээр бичигдсэн.
